## 1. Who it is for, and the one job of each screen

A general audience: anyone who wants to look back at their own recent activity, such as when a trip was and what they booked, without an account, a server or a cloud. The owner's photos and bookings are a test case, not the persona.

| Screen (iPhone tab) | One job |
|---|---|
| Timeline | Behind one unlock, show deterministic evidence for a chosen window, in four trails. |
| Ask | Answer a question over that evidence, streamed, with Stop and a tools-used row. |
| Add | Put one screenshot (a ticket, a confirmation) on the timeline, with sensitive text hidden before it is shown. |
| Privacy | Say plainly what iOS lets Pastport read, hold Connected tools (including Health), and Lock and Clear. |

## 2. Screens

Existing structure (cited): `RootView` switches on `horizontalSizeClass` — tabs when compact, timeline plus Ask side by side when regular (`Sources/PastportiOS/PastportApp.swift:33-55`); tabs are `TimelineModel.Tab.trail` and `.ask` only (`TimelineModel.swift:50-54`); scene-phase `.background` calls `lockAndClear()` (`PastportApp.swift:25-28`).

**Honest photo copy (replaces the earlier "images are never opened").** What the code does: for each photo in the window that is **not** a screenshot, `PhotoLibraryProvider` loads the image data on the device (`localImageData`, `PhotoLibraryProvider.swift:134-146`, `isNetworkAccessAllowed = false`) and runs Vision scene classification on it (`:96-104`, `:118-132`), keeping at most five label words per photo above 0.5 confidence (`reduceLabels`, `:254-262`). Screenshot assets are counted by metadata only and their pixels are never read (`:92-94`). Nothing is sent anywhere. For an iCloud-only asset (original not on the phone) the local request fails; the provider catches it, keeps the photo as a counted record with no labels, and never downloads it (`:100-103, 143`). So labels can be missing for photos that are not on the device. Required copy, used on the Locked screen, Privacy screen, `NSPhotoLibraryUsageDescription` (`project.yml:91`) and the README:
- "Photos are checked on this iPhone for scene labels, such as beach or food. Nothing leaves the device and no photo is kept. Screenshots are counted only. Photos stored only in iCloud are skipped."
- "Counted, not inspected" is true **only** for screenshots and must be worded that way; it must not describe ordinary photos. The prototype's "never opens them" and "Counted, not inspected" lines are corrected in the prototype by the owner (section 8, drift).

**Timeline (locked).** Before anything is read it shows: "Timeline is locked. Nothing has been read yet", the four window chips, an Unlock button, the honest photo line above, and one honest line: iOS does not let apps read Safari history. Person can: pick a window, unlock, or go to Add / Ask / Privacy.
- `unlock()` is **new behaviour** on iOS, not a presentation of existing state. Today `unlocked` is private and only the Mac history path sets it (`TimelineModel.swift:123, 292-297`); each photo read asks for Face ID or passcode with grace 0 (`:215-218`); adding a screenshot needs no authentication (`:238-262`). Definition for 2.0: `isLocked` is true from launch and after every `lockAndClear()`; `unlock()` = authenticate (same `Authenticating` call as today, grace 0), then request Photos access, then read the window; it sets `isLocked = false` only when the read pass completes or finds nothing (an empty or denied result still unlocks the screen and shows the status line). A failed or cancelled authentication leaves `isLocked` true and evidence empty. Screenshots added while locked stay in memory and are shown only on the Add tab; the Timeline shows them after unlock; `lockAndClear()` removes them (it already clears `screenshots`, `TimelineModel.swift:178-194`). Add never requires unlock because it reads no library.
- Changing the window chip while unlocked calls `lockAndClear()` today (`TimelineModel.swift:63-69`). Keep that: the chip change relocks and the person unlocks again. Say so in the chip footnote: "Changing the window locks the timeline."
- Error: Face ID mismatch shows "Could not unlock. Nothing was read." with Try again and passcode fallback (`LAContext` policy `deviceOwnerAuthentication`, `Auth.swift:13`, `Sources.swift:18-39`). New copy; behaviour exists in `Authenticating`.
- Empty (unlocked, nothing found): "Nothing to show yet. Allow read-only photo access, or add a screenshot of a booking." Existing status text: `PhotoEvents.statusLine(for:)` (`PhotoEvents.swift:28-`).
- Limited Photos access: line "Counting only the photos you shared with Pastport" (A6). New.
- Truncated window: if the window holds more than 500 photos, a line "Showing the newest 500 of N photos in this window" (slice 2). New.
- Offline: banner "Offline is fine. Timeline, Ask and screenshots run on this iPhone. Only Connected tools need a connection."

**Timeline (unlocked).** Window chips, then the trail chips, then evidence cards. Trails on iPhone (new type `TimelineTrail`, four cases): Overview, Travel, Photos, Privacy. The Mac `HistoryFocus` has five (overview, research, travel, privacy, places; `HistoryJourney.swift:4-9`); the Mac enum is not reused, because research and places need Safari history. `TimelineTrail` is a separate small enum in `PastportKit`, not a subset hack.
- Each card leads with one human sentence, a mono source label (PHOTO ACTIVITY, SCREENSHOT YOU ADDED), and a closed "How do we know this?" disclosure: what was read, in which window, "Cleared when you lock or leave the app". Numbers on cards are formatted by code from `PhotoEvent` (`photoCount`, `screenshotCount`, `PhotoEvents.swift:19-25`) and `AddedScreenshot`. A HEALTH source label exists only if slice 18 ships. The model never produces a card number.
- Photos trail: `PhotoEvents.cluster` output (`PhotoEvents.swift:43-78`). Copy follows the honest photo copy above.
- Travel trail: photo events (date range, photo and screenshot counts, scene labels) plus **booking cards from added screenshots** (built in slices 9 and 10). No place names (A2) and no claim that an event "is a trip": the card says "Photos on 3 days, 14 Jun to 16 Jun", not "Trip to X". Deterministic booking rule: see Add.
- Privacy trail: "Nothing sensitive found" or a count of redactions **by kind** (email, one-time code, card). Per-kind counts do not exist today: `redactionCount` is one total, `email + otp + card` (`ScreenshotReader.swift:34, 141`). API change (slice 8): `ScreenshotScrubber.scrub` (the `static func scrub`) returns `RedactionCounts { email, otp, card }` and `ScreenshotEvidence` gains `public let redactions: RedactionCounts`, with `redactionCount` kept as the computed sum so existing callers and tests do not change. Never shows the redacted text.
- Overview: the newest card from each other trail, at most five.
- Duo/regular width: Ask sits beside the evidence (section 6).

**Ask.** Existing `AskScreen` and `TimelineAssistant` (`TimelineAssistant.swift:108-215`). Prototype adds: chips for suggested questions per trail (slice 7), streamed answer, Stop, tools-used list, note "Kept only because every number in it appears in the evidence. The model phrases; Swift counts." (existing policy `TimelineAnswerPolicy`, `:113-125`).
- Offline works (on-device). Model unavailable: banner "Apple Intelligence is off", answer replaced by the recorded facts (`TimelineEvidence.countsLine`, `:35-41`) with one line saying why (`FoundationTimelineAnswerer.reason(for:)`, `:198`). Screenshot: `docs/screenshots/fallback-apple-intelligence-not-ready-ios.png`.

**Add.** Photo picker (no library-wide permission needed) → `ScreenshotReader.read(imageData:)` (`ScreenshotReader.swift:94`) → scrubbed lines, kind, per-kind redaction counts, then Add to timeline. The image is not kept. This tab is built in slice 11 (no earlier slice built it). The prototype shows redaction as filled bars and the line "Emails, one-time codes and card numbers are replaced before you see it." Error: no text found → "No text found. Try a clearer screenshot." (new copy).
- **Booking detection reuses `Booking.Kind`** (`Bookings.swift:17-22`: confirmation, itinerary, checkout, ticket) instead of a parallel `BookingFromScreenshot.Kind`. `BookingFromScreenshot` carries a `Booking.Kind`, a date and a title line; `lodging` is not a new kind (a hotel confirmation is `.confirmation`).
- **Classifier precedence** (the existing `ScreenshotKindClassifier` checks banking, then chat, then receipt, `ScreenshotReader.swift:166-183`): banking → chat → booking (new) → receipt → unknown. A ferry e-ticket that also says "amount paid" is classed **banking** today because "amount paid" is a banking marker and banking wins; for 2.0 the booking check runs before the banking check **only when** the scrubbed text has a ticket marker (boarding pass, e-ticket, PNR, "check-in") **and** a date, and contains none of the stricter banking markers other than "amount paid"; otherwise banking still wins and no booking card is made. This keeps the stricter label for real bank screens. "confirmation number" is a receipt marker today (`:156-160`); a screenshot with a date plus a ticket marker becomes a booking, otherwise it stays a receipt.
- `ScreenshotKind` gains no case; the booking card is derived (`BookingFromScreenshot.detect(evidence)`), and the narration opt-in (`requiresNarrationOptIn`, `:22-26`, true for every kind) is unchanged: a booking card's text never reaches a model without the existing opt-in. Chat, banking and receipt text stay excluded.

**Privacy.** Four cards: What iPhone can read (Photos activity counts and scene labels, screenshots you add; not Safari history; the honest photo copy), Connected tools (existing `ConnectedAssistant`, per-request Allow once or Decline, never receives timeline data, `ConnectedAssistant.swift:117-165, 183-202`; with the risk tier table in section 7a and the receipt list), optional Health (Connected tool today; timeline totals only if A1 flips), and Lock and Clear.

## 3. On-device AI (Foundation Models)

Pattern reference: **the repo's own** `JourneyDynamicProfile` (`HistoryJourney.swift:1049-1086`): a `LanguageModelSession.DynamicProfile` keyed on the current focus, with an immutable snapshot published through a locked state object (`JourneyProfileState`, `:515-541`), behind `#if compiler(>=6.4)` and `@available(macOS 27, iOS 27, *)`. 2.0 copies that shape for the timeline and does **not** introduce a second parallel pattern or import Origami's. Origami remains a reference only for: a tool that proposes and the person confirms (`Origami/Coach/MovePhotoToStepTool.swift`) and `Error+DisplayMessage` for unavailability.

Today: one `LanguageModelSession` per question with three read-only tools `timeline_counts`, `photo_activity`, `added_screenshots` and `@Generable TimelineAnswerPayload { answer }` (`TimelineAssistant.swift:144-215, 238-281`). Unit tests use `TimelineAnswering` fakes (`ScriptedAnswerer`, `TimelineModelTests.swift:18`) and never call the model.

Change for 2.0:
1. **Profile per trail.** A `TimelineProfileState` + `TimelineDynamicProfile` mirroring the Journey pair, keyed on the current `TimelineTrail`. Travel: tools `photo_activity`, `added_screenshots`, `bookings` (new, reads `BookingFromScreenshot`). Photos: `photo_activity`, `timeline_counts`. Privacy: `timeline_counts` and `redaction_summary` (new, per-kind counts) only — it gets **no** screenshot text. Overview: the three existing tools. History transform keeps instructions plus the last four entries (same shape as Orbit `OrbitFoundationHistoryPolicy` and Breakline `CoachProfile.shortHistory`). On iOS 26 the current `LanguageModelSession(tools:instructions:)` path stays (deployment target is 26.0, `project.yml:7-8`); the choice of tools per trail is a pure function `TimelineTools.names(for: TimelineTrail)` shared by both paths, so it is unit-testable without the model.
2. **Health tool (conditional, slice 18).** Only if A1 flips: `health_daily_totals` returns per-day steps and distance for the window from `HealthDay` values, registered only when the Health toggle is on and the person has completed the system prompt.
3. **Typed output.** `TimelineAnswerPayload` gains `evidenceKinds: [EvidenceKind]` (`@Generable enum`: photoActivity, screenshot, and health only if slice 18 ships) so the UI can show which source labels the answer used. Code intersects it with the tools actually called; a claim with no matching call is dropped.
4. **Fallback.** Unchanged and required: when `SystemLanguageModel.default.availability != .available`, deterministic summary plus a reason line; no empty or invented answer.

Model decides: which tool to call, the wording. Code decides: all counts, dates, windows, which screenshot text is eligible, the number-subset check, and what data exists.

Observation from the sibling bench (not a Pastport result, unverified here): the on-device model formats numbers loosely, so cards render numbers from data and the number check stays.

## 4. Data and safety boundaries

- Read-only everywhere: Photos activity (counts and on-device scene labels), screenshots the person adds, and (Connected tools only) the sources in section 7a. Photos never download from iCloud (`isNetworkAccessAllowed = false`, `PhotoLibraryProvider.swift:143`). Photos access level: the app requests `.readWrite` and accepts `.limited` (A6); it never writes to the library.
- Needs the person's approval: Face ID or passcode before a read (`Authenticating`); Photos permission at first read; every Connected-tools call (Allow once, bound to the request ID and generation and removed after one use, `ConnectedAssistant.swift:117-165, 183-202`; it expires on lock, background or tool change; there is no time-based expiry).
- Everything read is cleared on lock and when the app leaves the foreground (`PastportApp.swift:25-28`). No account, no server, no analytics.
- No money handled; no `Decimal` in scope.
- Place: no photo coordinates are read in 2.0 (A2). `PhotoRecord` carries no location (`PhotoEvents.swift:5-15`) and that stays so. Reverse geocoding (`MKReverseGeocodingRequest` or `CLGeocoder`) sends coordinates to Apple's servers, which would contradict "Offline is fine" and "no server"; hence the default.
- Oldest-first cap: today photos are fetched oldest first with a limit of 500 (`PhotoLibraryProvider.swift:82-83`), so a busy 90-day or 1-year window silently counts only its earliest 500 photos. 2.0 reads **newest first** and discloses the cut (slice 2).
- App Review 2.5.19: demo mode and `--ask` launch arguments are already inside `#if DEBUG` (`PastportApp.swift:14-22`) — the gate must re-verify after every slice. An App Intent must have a tested, visible caller or not ship (slice 17). Entitlement note: `PastportiOS.entitlements:6-9` declares HealthKit and `project.yml:97` carries `NSHealthShareUsageDescription`; Health **is** a visible iOS feature today: Ask → "Answer from" (icon-only menu, `SharedControls.swift:38-53`) → Connected tools (`PastportApp.swift:91-92`) → Health button (`ConnectedAssistantView.swift:54-74`), registered at `ConnectedAssistant.swift:605-608`, backed by `HealthTool` in `FoundationModelsKit` at revision `65834b1`, which reads steps, heart rate, workouts, sleep, active energy and distance, read-only (`requestAuthorization(toShare: [], read:)`). It is not in the "What's new" draft (`RELEASE-READY.md:47-51`). Therefore: (a) the entitlement and usage string stay in 2.0 by default; (b) the App Store notes and review notes must name Health under Connected tools and list the data types; (c) **if the owner drops Health entirely**, one commit removes `.health` from the iOS Connected-tools picker (`ConnectedAssistantPolicy.isAvailable`), the entitlement and the `NSHealthShareUsageDescription` string together. Removing only the entitlement and string would leave the button enabled, since `isHealthDataAvailable()` is true on iPhone, and requesting authorization with no usage string crashes the app.
- Run the `hidden-feature-gate` skill before reporting any slice done.

Reduce Motion: no pulsing or flashing anywhere (prototype uses none); streamed text appears in place and, under Reduce Motion, all at once. Dynamic Type: text styles only; evidence cards reflow, mono source labels wrap. VoiceOver: each card is one element reading "Source, sentence, N details"; disclosure announces expanded/collapsed; redaction bars read "Hidden: email address" (kind only, never content; needs the per-kind counts from slice 8); Send/Stop have labels; locked screen reads "Timeline locked". Tap targets at least 44 pt. Contrast: the prototype palette (`DESIGN.md`) is measured in slice 7; any pair under 4.5:1 for body text (3:1 for large text) is fixed before the screens ship. Owner safety rule, repeated in every UI brief: nothing pulses, flashes or blinks; no streaming cursor; no Marvel/DC-style IP.

### 7a. Connected tools: risk tier per tool

Source: `ConnectedAssistant.makeTools` (`ConnectedAssistant.swift:581-612`) and `ConnectedAssistantView.swift:54-74`. Rules already in code and now part of the contract: a tool is **off by default** (`selectedTools` starts empty, `:348`), at most three can be selected (`maximumSelectedTools = 3`, `:89`), every call waits for Allow once or Decline, and every call leaves a receipt with its arguments and status (`toolReceipts`, `ConnectedToolReceipt`, `ConnectedAssistantView.swift:104-119`). There are **no write tools** today. The receipt list must stay visible; removing it is a spec violation.

Tier A = reads data that stays on the device. Tier B = sends something off the device. Tier W = writes (none exist; adding one needs a new spec).

| Tool | Tier | What leaves the device | Service in code | Off by default |
|---|---|---|---|---|
| Contacts | A | Nothing; search and read only (`permitsContactAction`) | Contacts | Yes |
| Calendar | A | Nothing; read tool only | EventKit | Yes |
| Reminders | A | Nothing; read tool only | EventKit | Yes |
| Health | A | Nothing; read-only, steps, heart rate, workouts, sleep, active energy, distance | HealthKit | Yes |
| Music | A/B | Now playing stays local; a catalog search is sent to Apple Music; playback controls unavailable (`permitsMusicAction`) | MusicKit | Yes |
| Location | A/B | Device position is read locally; map lookups go to Apple | Location + MapKit | Yes |
| Weather | B | The place or coordinates you ask about, to Open-Meteo, plus MapKit | Open-Meteo + MapKit | Yes |
| Web | B | Your search words, to a third party | Search1API | Yes |
| Web metadata | B | A request to the URL's host (your IP and the URL) | URLSession | Yes |

Decision for 2.0 (default, section 8): all nine ship, all off by default; Tier B rows show the label "Sends data off this iPhone" in the picker and in the Allow once sheet (the sheet already shows arguments and destination, `ConnectedToolApprovalRequest`). Unverified: the A/B split for Music and Location rests on the tool names and service strings, not on a read of the dependency; slice 13 reads them before writing the labels.
